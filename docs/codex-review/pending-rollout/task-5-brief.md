## Inspected source and root rulings

- The public `goal_finance_apply(p_request_id uuid,p_command jsonb,p_quote jsonb DEFAULT NULL)` dispatcher lives in lifecycle SQL; it calls private `goal_transaction_apply` for transactions. The newest purchase-date migration replaces the latter and `goal_transaction_quote`. Extend those final definitions additively, retaining all existing reservation/lifecycle branches and purchase-date metadata. Do not copy an older dispatcher over the current one.
- **Approved ruling:** Replace only the credit payment's transaction-month ceiling in `goal_transaction_quote` with authoritative account outstanding debt. An opening-only account currently has zero transaction-derived month debt and cannot be paid. Retain transfer input, actual payment date, `amount <= outstanding`, cash availability, reservation release and quote freshness checks. Allocation is global oldest dated obligation first, then undated residual. The selected-month preview is context, not a payment restriction. Overpayment remains rejected.
- **Approved ruling:** Use a private union adapter: opening row ID is `debt_due_rows.id`; purchase row ID is its actual `transactions.id`; purchase group is proven `installment_group_id`, otherwise that transaction's own UUID. Never group by description, manufacture transaction rows, infer purchase dates, or create a second purchase schedule.
- **Approved ruling:** Correction retains the original purchase transaction and paid/payment history. Ordinary `delete_transaction` must fail closed with `INVALID_STATE` for a purchase referenced by settlement/correction events. Unreferenced unpaid purchases can retain validated old single-delete behavior. Payment deletion remains its existing actual-money reversal, plus reversal of its original debt settlement events. Do not reverse corrected principal twice.
- Historical paid amounts can be reconstructed only from actual owned operation/transaction provenance. Missing or ambiguous history produces `needs_review`; never invent historical settlements. Task 6a exposes that condition before UI adoption is enabled.
- **Approved ruling:** Extract the unchanged shared money schema primitives into an acyclic leaf module and preserve goals contract re-exports. This small refactor affects every financial schema consumer, so existing goal/client/controller regressions are required before accepting it.

Define these **new** contracts explicitly, preserving 4a/4b exports:

```ts
export type CorrectDebtRowsCommand = {
  kind: 'correct_debt_rows'; accountId: string; rowIds: string[]; fingerprint: string;
};
export const CorrectDebtRowsCommandSchema: z.ZodType<CorrectDebtRowsCommand>;
```

The schema is strict, requires UUID account/row IDs, 1..600 unique row IDs, and a lowercase 64-character SHA256 fingerprint. Add this member to `FinancialCommandSchema` by importing the debt schema. Avoid the runtime cycle when creation/adoption schemas need the existing money schemas: move only the unchanged `Money` type, `MoneySchema`, `SignedMoneySchema`, `PositiveMoneySchema` and their private safe-centavo predicate from goals contracts into `src/lib/money/contracts.ts`; import/re-export them from goals contracts to preserve every current API, and have debt contracts import from the leaf money module. This is extraction of the same validator, not a new money pipeline. Debt contracts must not import goals contracts/summary at runtime. Cover old money schema outputs in existing tests before the move. SQL normalizes the selected IDs in sorted UUID order for command identity; duplicate IDs reject before normalization. Array order alone is not a different selected set. `applyFinancialCommand(requestId,command)` uses no transaction quote for this command and returns the unchanged `FinancialResult` shape `{ operationId, transactionIds, replayed }`; correction returns `transactionIds: []` because it creates/deletes no actual transaction.

Private SQL contract for both units and 6a:

```sql
public.debt_account_state(p_owner uuid,p_account_id uuid) RETURNS jsonb
```

It has no client EXECUTE grant, fixed search path and explicit owner predicates. Its JSON is `{ account, rows }` using the complete account/row shapes in [6a](task-6a-brief.md). It computes exact unpaid amounts and the account fingerprint from sorted owned account identity/balance, canonical due/purchase rows, settlement/correction/reversal events and proven history state. No timestamps alone, client-selected fields, rounded display strings or description matching as a fingerprint. 6a reuses this exact helper, so correction compares a fingerprint the frontend can actually receive.

Create owner-scoped `debt_settlement_events` and `debt_correction_events`, with `id`, `user_id`, `account_id`, `operation_id`, exact unconstrained numeric positive `amount`, `created_at`, and exclusive target columns `opening_due_row_id`, `purchase_transaction_id`, `residual_account_id`. Settlement allows exactly one of three targets; correction allows exactly one opening/purchase target and never residual. Each owner-composite target FK references 4b due rows, existing transactions or accounts respectively; operation FK references `(user_id,id)` financial operations. Add source `(user_id,id)` uniqueness where a referenced existing table lacks it. No cascade may destroy ordinary financial history.

Settlement events additionally store `kind: 'settlement'|'reversal'`, `payment_operation_id`, `payment_transaction_id` (immutable audit UUID), and `reversal_of` referencing the original event with owner-composite FK and unique nonnull reversal reference. The payment operation survives existing physical payment deletion; do not put a restrictive payment-transaction FK on that audit UUID. Validate it against the actual operation/result/transaction at allocation. Reversal target/amount/payment provenance must equal its source. A reversal is a positive amount with kind determining its sign, not a mutable paid counter. Correction events are positive immutable principal removed. Enforce scale <=2, finite values, creation/storage range, owner/account consistency and exactly one valid target in SQL; derive counters from events.

Enable owner SELECT RLS; authenticated gets SELECT only on event tables. Reject client insert/update/delete; revoke PUBLIC/anon/authenticated/service_role helper EXECUTE. Preserve existing public dispatcher/quote grants without broadening them. Extend the account history delete guard for new event references while retaining its auth-user cleanup exception and all old checks. A privileged wrong-owner target must fail its FK. Apply the same guard/fixed-search-path discipline as 4b.
